# AAAAT Product Context

**Explanatory context, not product authority.** [Product Definition](PRODUCT_DEFINITION.md) and current explicit Product Owner instruction govern. Git history preserves the historical notes and conversations from which this context was recovered.

## Friction is the central problem

AAAAT grew from keeping offer material, recalling an opportunity during a recruiter call, reusing professional information and adapting documents. Fewer clicks, less retyping, less searching and less reconstruction are the goal. More automation is useful only when it serves that goal.

A technically elegant implementation can still fail if it makes the user maintain stages, priorities, schemas or AI routines. A visual simplification can also fail if it removes useful control or turns recognisable information into a flat grid of empty boxes.

## Several equally valid starting points

A user may have a recruiter on the phone, a fragment to save, useful facts to enter, a CV to revise, career information to update or an external assistant already doing broader work. These are peer intentions, not stages of one required workflow.

Job discovery happens wherever the user chooses. AAAAT begins when useful material or a bounded operation reaches the workspace; it does not need to own discovery, model advice or application lifecycle management.

## Capture retains what exists now

Raw material is useful before it is structured. Keeping the source beside editable information lets a person paste or copy values without context switching. At narrower sizes the areas can stack without becoming separate wizard steps.

Optional AI processing is a choice beside that work. Manual entry remains complete. An empty value need not require the same confirmation as overwriting human work; existing/newer edits remain protected. The original Source survives extraction.

## Recognition through content and typography

The time-pressure example is simple: a company or role is mentioned, the user finds the application quickly and recovers context while listening. This calls for compact recognition plus richer inspection, not separate competing Focus/All-data products.

The accepted application covers use actual content, user-selected order and typographic prominence. Each application becomes recognisable by composition as well as its words. Expansion gives roughly twice the width and height, anchors near the outer edge and moves neighbours aside. It adds useful content rather than blank padding.

Read-first is not read-only. Small star, eye, sparkle, pencil and gear controls let the user adjust precisely what they need. Ordinary editing remains readable forms; copying cover typography into editors confuses two different intentions.

## Defaults remain yours to change

Useful information varies across professions. A pilot may want flight hours and licences; a software engineer may want stack or work arrangement; a writer may want format or rights. Developer-supplied fields, career groups and section names are conveniences, not a permanent ontology.

Tags are a lightweight shared glossary. One definition can help across applications. Tag names belong in the cards; meanings belong in the rail monitor. New AI-proposed categories remain editable before creation because differently named concepts may overlap.

## Documents are independently core

A session may simply create a CV or letter, render/export and leave. Application context helps organise relevant documents but is not a prerequisite.

Reusable facts, saved variations, templates, editable documents and generated artifacts have different purposes. A change in this CV must not silently rewrite reusable facts. Opening an editor is not a decision to keep a permanent document. Generated output should remain useful even after an editable source is removed.

## Optional AI, bounded local ownership

Inside AAAAT the user asks for help with a Source, field, CV or letter. AAAAT prepares allowed context and validates the result; it owns no model or inference. The external provider owns its reasoning and service behaviour.

Another AI environment is also a valid entrance. The local request should be editable and understandable without hidden context rebuilding. Connected permission controls future reads only; it cannot undo a completed disclosure. Interview requests remain a secondary application-linked convenience, not advice the product endorses.

Local storage, local presentation and AI exposure are distinct. The UI should express these choices without turning ordinary work into a privacy console or repeated consent ceremony. Actual context can be inspected when useful.

## A small, coherent product

Fixed navigation and contextual top-bar actions leave the work area for information. AI events and diagnostics appear on demand. Setup, recovery, TeX and external-host details belong where relevant, not in the first impression of ordinary work.

AAAAT is maintained by one developer with AI assistance. Proven local ownership, typed mutation boundaries, renderer isolation and portable artifacts matter. Generic frameworks, migration programmes for disposable development states and generated governance machinery do not become useful merely because they are conventional.

Historical plans, tests and successful builds are evidence only. The owner evaluates the product; engineering verifies the affected mechanisms and reports the limits honestly. Preserve the accepted direction while correcting the concrete defects, rather than starting another additive redesign.
